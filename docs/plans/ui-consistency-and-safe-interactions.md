# UI 일관성·단계적 정보 노출·안전한 조작을 위한 Forge 수정 계획

작성일: 2026-11-05

상태: 구현과 로컬 검증 완료, 릴리스 진행. 2026-11-05 사용자가 이 계획에 따른 수정·배포와 현재 디바이스의 최신 버전 업데이트를 승인했다. 정본 계약과 검증 근거는 아래 실행 기록으로 연결한다.

## 목표와 범위

Forge가 UI를 설계·구현할 때 제품의 디자인 컨셉과 같은 역할의 표현을 일관되게 유지하고, 현재 작업에 필요한 정보와 다음 행동을 우선하도록 한다. 기능의 숨김·읽기 전용·비활성·확인 실패를 구분하며, 사용자가 준비할 수 있는 조건은 해결 경로와 함께 안내한다. 삭제 등 위험도가 높은 작업은 대상과 영향을 이해한 뒤 명시적으로 확정하게 한다.

기존 제품의 시각적 개성과 플랫폼 관례는 유지한다. 범용 폰트 크기·버튼 높이·카드 구조·색상·모달 형식을 정하지 않는다. 관련 기준이 없으면 사용자 방향과 실제 작업에 맞는 최소한의 일관된 기준을 선택하고, 작은 수정마다 디자인 시스템 구축이나 별도 문서를 요구하지 않는다. SQL 최적화 가이드와 위피 애플리케이션 코드는 이번 수정 범위에 포함하지 않는다.

## 확인한 원인과 현재 계약

- 위피 공개 웹의 기본 버튼 12px `!important`, 실제 커뮤니티 14px `!important`, 주요 행동 16px 선언이 충돌했다. 실제 소스 CSS와 버튼 클래스의 격리 브라우저 재현에서 최종 글자 크기는14px이었다. 운영 화면 전체의 관찰 결과와는 구분한다.
- 어드민은 공통 타이포그래피·크기 옵션이 있지만 일부 규칙이 특정 DOM 구조에 의존하고 화면별 규칙도 존재한다. 로컬 실제 컴포넌트에서 환경 행40px·탐색36px은 정상 적용됐다. 차이가 있다는 이유만으로 모든 화면을 결함으로 분류하지 않는다.
- 최근 작업 기록에는 번역 실행보다 반복 비용 설명이 앞서는 문제, 이벤트 제목보다 무료 횟수가 강조되는 문제가 있었다. 과거 관찰과 후속 개선 기록을 현재 미해결 결함으로 단정하지 않는다.
- 어드민의 UI 크기 회귀 검사는 존재하지만 기본 critical E2E 목록에는 포함되지 않는다. 기본 명령의 성공만으로 UI 품질을 증명할 수 없으며, 별도 실행 여부는 개별 증거로 확인해야 한다.

기존 [UI 디자인 스킬 분리 계약](../specs/forge-ui-design-skill-separation/forge-ui-design-skill-separation.md)은 전문 디자인 스킬 설치를 요구하지 않고, Forge의 책임을 제품 맥락과 검증에 둔다. [디자인 품질 계약](../specs/web-app-design-quality/web-app-design-quality.md)은 역할 일관성·정보 노출·의미색·상태 보존을 이미 다룬다. 이번 변경은 이 의미를 보존하면서 구현 전 판단과 위험 작업·선행 조건 안내를 명확히 연결한다.

## 변경할 지침

### 제품 컨셉과 같은 역할의 표현을 구현 전에 연결한다

기존 제품·승인된 디자인 시스템·관련 컴포넌트를 먼저 확인한다. 현재 작업의 주 행동, 보조 행동, 제목, 본문, 상태와 보조 정보를 구분하고 적절한 기존 표현에 연결한다. 이는 판단 기준이며 역할 선언표를 매번 작성하라는 절차가 아니다.

폰트는 크기뿐 아니라 굵기·줄높이·대비·간격을 함께 다룬다. 버튼은 역할별 크기·정렬·레이블·상태를 함께 다룬다. 서로 다른 역할이나 플랫폼에 필요한 차이는 유지한다. 잘못된 기존 화면을 일관성의 기준으로 복제하지 않고, 계약과 실제 기준이 충돌하면 해당 범위를 확인한다.

구현에서는 기존 토큰·컴포넌트·variant를 우선 활용한다. 웹의 중복 규칙, specificity, 상속, 로드 순서, `!important`가 의도한 역할을 덮는지 필요할 때 추적한다. `!important` 전체 금지나 모든 개별 CSS 제거를 요구하지 않는다. Native UI에서는 해당 스타일·컴포넌트 체계를 확인한다.

### 필요한 정보와 다음 행동을 단계적으로 제공한다

현재 판단과 행동에 필요한 내용은 기본 화면에, 드물게 쓰는 상세·근거·진단은 명확한 상세 진입 뒤에 둔다. 작업과 무관하거나 같은 의미를 반복하는 내용은 생략한다. 오류·차단·비용·위험 등 현재 결정에 영향을 주는 내용은 발견 가능하게 유지한다.

단계 분할이나 접기를 목표로 삼지 않는다. 비교해야 하는 값과 실행 조건·행동을 불필요하게 떨어뜨리지 않고, 진행에 따른 상세 노출에서도 입력·선택·초점·관련 화면 상태를 보존한다. 시스템 구현 사정은 사용자의 판단에 필요한 경우에만 설명한다.

### 숨김·읽기 전용·비활성·확인 실패를 구분한다

- 현재 작업과 관계없는 기능은 생략하거나 적절한 위치로 이동한다.
- 값 확인은 필요하지만 편집할 수 없으면 읽기 전용으로 제공한다.
- 사용자가 선행 설정을 완료하면 사용할 수 있는 관련 기능은 발견 가능하게 두고, 부족한 조건·활성화 방법·실제 설정 위치를 안내한다. 원래 기능은 조건 충족 전 실행되지 않아야 한다.
- 처리 중, 준비 조건 부족, 권한 부족, 조회 실패를 같은 회색 비활성 상태로 뭉뚱그리지 않는다. 확인 실패를 기능 없음이나 설정 미완료로 오인시키지 않는다.
- 권한 제한의 노출·숨김·권한 요청 경로는 제품 계약을 따른다. 사용자가 접근할 수 없는 설정을 해결책으로 제시하지 않는다.
- 중요한 이유와 해결 경로는 비활성 요소의 hover에만 의존하지 않고 키보드·터치·보조 기술로도 발견 가능하게 제공한다. 준비 설정까지 잠가 순환 의존을 만들지 않는다.

### 위험도가 높은 작업은 실행 전에 명시적으로 확인한다

삭제, 중요한 권한 변경, 서비스 중지 등은 이름만으로 분류하지 않고 실제 영향 범위와 복구 가능성을 판단한다. 위험도가 높은 작업은 대상·범위·주요 영향·복구 가능 여부를 보여준 뒤 구체적인 실행 문구로 확정하게 한다. 단순한 “계속하시겠습니까?”나 위험색만으로 의미를 대신하지 않는다.

확인 화면 열기·취소·Escape만으로 명령을 보내지 않으며, 실수로 확정하기 쉬운 초기 초점·키 동작을 피한다. 모달·확인 페이지 등은 제품과 플랫폼에 맞게 선택한다. 이미 같은 대상과 영향을 충분히 확인하는 단계가 있으면 중복 확인을 추가하지 않는다. 이름 재입력·추가 인증은 실제 위험이나 소유 계약이 요구할 때만 사용한다.

실행 중 중복 제출 방지, 확정 성공·실패·결과 미확정의 구분, 실패 시 입력 보존과 복구 경로를 다룬다. 작업을 전송한 뒤 확인창을 닫는 행위를 서버 작업 취소나 성공으로 표현하지 않는다. UI 확인은 서버 권한·최신 상태·원자적 보호를 대신하지 않는다. 위험도가 낮고 쉽게 되돌릴 수 있는 조작에 불필요한 확인을 늘리지 않는다.

이 지침은 제품 UI의 최종 사용자 확인에 관한 것이다. 코딩 에이전트가 이미 승인받은 구현 작업마다 채팅으로 재승인받는 규칙으로 확대하지 않는다.

신규 독립 스킬·별도 디자인 패키지·전용 UI 템플릿·validator의 시각 수치 규칙은 추가하지 않는다. 배포 스킬은 영어, 사용자용 계획과 설명은 한국어를 유지한다.

## 실행 순서와 완료 증거

1. **정본 변경안을 반영한다.** 구현 착수 시 현재 baseline과 승인 범위를 확인하고 두 계약의 책임·Requirements·Acceptance를 함께 수정한다. 기존 상태 보존·재정렬·접근성·플랫폼 예외는 유지한다. 스펙 검증을 통과한 뒤 스킬 변경이 그 의미에 의존하게 한다.
2. **공통 원문과 조건부 연결을 구현한다.** `ui-work.md`에 판단 기준을 모으고 계획·실행·검증에서 같은 기준을 참조한다. 모든 작업의 필수 절차가 되거나 기존 전문 디자인 스킬과 역할이 충돌하지 않는지 검토한다.
3. **실제 결과를 평가한다.** 아래 대표 시나리오를 기존/변경 지침에 같은 조건으로 적용한다. 독립 에이전트가 가능하면 같은 모델·환경의 새 문맥을 사용하고 결과물과 실제 동작을 검토한다. 위피 재발 사례는 합성 자료와 격리 fixture로 축소하며 실제 저장소나 운영 데이터를 수정하지 않는다.
4. **구조와 배포 경계를 검증한다.** 포맷·링크·스펙 검증 및 `bash scripts/validate.sh`를 실행하고 `validate: all checks passed`를 확인한다. 필요한 격리 설치에서 새 reference가 포함되고 제거했던 디자인 스킬은 복구되지 않는지 확인한다. 특정 플랫폼 시뮬레이션을 실제 통합 검증으로 보고하지 않는다.
5. **차이와 한계를 전달한다.** 지침의 실행 효과, 발견해 수정한 문제, 미검증 범위를 기록한다. 계획 완료와 스킬 구현 완료, 로컬 검증과 배포를 구분한다. 배포가 요청되면 maintainer 지침에 따라 outgoing 변경을 확인하고 두 plugin 버전을 올려 재검증한 후 릴리스한다.

정본 변경 후 실행할 명령:

```bash
bash plugins/forge/skills/writing-specs/scripts/spec-docs.sh --repo-root . validate --root docs/specs --baseline-ref HEAD
bash scripts/validate.sh
```

이 명령은 후속 구현의 검증이며 계획 작성만을 위해 스킬 변경이나 전체 구현 테스트를 실행하지 않는다. 이번 계획의 완료 기준은 요청 항목·출처·수정 위치·의존 순서·검증 결과 조건·범위가 빠짐없이 기록되고 로컬 참조가 유효한 것이다.

## 대표 행동 검증

| 시나리오와 압력 | 통과해야 할 관찰 |
| --- | --- |
| 기존 화면 복사를 재촉하면서 같은 역할의 버튼·제목 스타일이 서로 다른 UI를 추가하도록 요청 | 기존 계약과 재사용할 역할을 식별하고, 우발적 불일치와 의도된 차이를 구분한다. 새 전역 덮어쓰기로 모든 크기를 평탄화하지 않는다. |
| 주요 버튼의 강조 선언이 공통 스타일에 가려졌지만 빌드가 통과 | 실제 계산 스타일·렌더링으로 충돌을 찾아 영향 범위에서 해결한다. 코드의 선언만으로 성공을 보고하지 않는다. |
| 모든 비용·설명·진단을 첫 화면에 넣으라는 압력 | 필수 비용·위험·차단은 남기면서 반복/상세 정보를 정리하고 주 행동을 찾을 수 있게 한다. 무조건 숨기거나 단계 수를 늘리지 않는다. |
| 외부 연결이 없는 기능을 빨리 숨기거나 회색 버튼만 두도록 요청 | 부족한 조건과 접근 가능한 설정 경로를 보여주고 조건 충족 전 실행을 막는다. 설정 화면으로 이동하고 돌아와도 관련 초안을 보존한다. |
| 준비 상태 조회 실패 또는 설정 권한 부족 | 실제 미설정과 구분하고, 가능한 재시도·권한 요청·담당자 안내를 선택한다. 도달할 수 없는 설정으로 보내지 않는다. |
| 급한 일정 때문에 삭제 확인 생략 요청 | 대상·영향·복구 가능성을 담은 명시적 확정을 유지한다. 취소/Escape는 명령0건, 확정은 중복 제출 없이 실행되며 실패·미확정도 식별된다. |
| 이미 최종 확인이 있는 작업 또는 낮은 위험의 되돌릴 수 있는 조작 | 같은 확인을 중첩하거나 모든 클릭에 확인창을 추가하지 않는다. 지원되지 않는 undo를 약속하지 않는다. |
| 웹·네이티브의 국소 수정, 긴 번역·확대·키보드 사용, 브라우저 부재 | 해당 플랫폼과 영향 범위의 증거를 선택한다. 웹 전용 절차·고정 픽셀·전체 상태 전수 검사·스킬 설치를 강제하지 않고 관찰 불가 범위를 밝힌다. |

위 시나리오는 스킬을 평가할 입력이며 모든 제품에 복제할 UI 패턴이 아니다. 모든 경우에 새 테스트를 요구하지 않고, 실제로 위험한 회귀를 잡는 기존 검사나 집중 관찰을 사용한다. 기본 테스트 명령이 필요한 UI 검사를 포함하는지도 확인한다. 작은 수정에서 전체 UI 감사를 시작하면 비례성 실패로 평가한다.

실행 기록에 확인한 결과만 완료로 기록한다. 후속 구현 중 실패하면 해당 지침을 수정하고 영향을 받은 시나리오만 다시 평가한다. 기존 사용자 변경을 reset하지 않으며 이번 변경 파일과 diff를 기준으로 복구한다.
