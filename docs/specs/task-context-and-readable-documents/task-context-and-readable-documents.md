# 작업 컨텍스트와 읽기 쉬운 문서

## Documents

- root: [작업 컨텍스트와 읽기 쉬운 문서](task-context-and-readable-documents.md)

## 목적

Forge는 사용자의 의도와 프로젝트 지식을 정확한 작업으로 연결한다. AI에는 현재 작업에 필요한 근거를 제공하고, 사람에게는 동작과 변경 영향을 이해하고 판단할 수 있는 설명을 제공한다. 두 소비자가 서로 다른 정본을 관리하지 않도록 같은 원문을 참조한다.

원문은 동작과 이유, 조건과 예외를 설명한다. 형식은 내용에 맞춰 선택한다. AI가 읽을 요약이나 사람에게 보여줄 설명을 위해 원문을 특정 제목이나 화면 구조에 맞춰 다시 작성하지 않는다. 형식과 도구는 실제 소비 기능으로 판단하고 기존 호환성만을 위해 유지하지 않는다. 컨텍스트 수집과 설명은 일반 Markdown과 코드도 사용할 수 있다. 현재 Spec의 승인·연결·경로 검증과 폐기된 뷰어용 Plan 문법은 구분한다.

## 동작 예시

작업자는 요청의 목표와 관련 계약을 읽고, 영향을 받는 구현과 테스트를 선택한다. 조건이나 예외가 다른 문서에 있으면 함께 확인한다. 문서와 구현이 다르면 승인된 의도, 관찰한 구현, 검증한 결과를 구분한다.

기존 검색과 읽기로 충분하면 별도 파일을 만들지 않는다. 다른 작업자에게 전달하거나 나중에 변경을 확인해야 하면 선택한 파일을 snapshot으로 묶을 수 있다. `source_context.py`는 원문을 그대로 담고 파일 경로와 hash를 기록한다. 관련성, 승인 상태와 의미는 도구가 추론하지 않는다.

사람에게는 요청에 맞는 설명을 작성한다. 처음 읽는 사람에게 목적과 동작을, 변경 검토자에게 변경 전후와 영향·미확인 사항을, 작업 인계자에게 진행과 다음 행동을 설명한다. 원문 링크에서 자세한 근거를 확인할 수 있다.

저장한 설명의 원문이 바뀌었는지 확인할 때는 기록한 파일의 bytes를 현재 파일과 비교한다. 원문이 그대로여도 설명에 오류가 있을 수 있고, 원문이 바뀌어도 의미가 같을 수 있다. 변경 감지는 다시 읽을 범위를 알려 주며 의미 검토를 대신하지 않는다.

## Requirements

### Forge는 하나의 원문에서 작업 컨텍스트와 독자 설명을 제공해야 한다.

작업 컨텍스트와 독자 설명은 파생 정보다. 원문 링크와 필요한 인용으로 중요한 판단을 추적하고 승인된 의도, 실제 구현, 검증 증거와 미확인 사항을 구분한다. 파생 요약이나 출처의 일치만으로 정책을 승인하거나 구현 완료를 선언하지 않는다.

### 작업 컨텍스트는 목표에 관련된 조건과 예외를 포함하고 필요한 원문으로 확장할 수 있어야 한다.

요청, 관련 계약, 영향받는 구현·테스트, 미해결 판단과 완료 조건에서 필요한 범위를 선택한다. 요약은 근거의 위치를 남기고, 관련 의존성이나 반례가 발견되면 범위를 넓힌다. 모든 문서 로딩이나 매번 별도 컨텍스트 파일 생성을 요구하지 않는다. 저장소에서 확인 가능한 사실은 조사하고 사용자만 결정할 수 있는 불명확함만 질문한다.

### 선택형 컨텍스트 도구는 문서 형식에 의존하지 않고 선택한 원문과 변경 근거를 보존해야 한다.

`using-forge/scripts/source_context.py`의 `capture`는 명시된 저장소 내부 UTF-8 파일의 전체 내용, 경로와 SHA-256을 JSON으로 표준 출력한다. 입력 문서에는 frontmatter, 영어 제목, statement ID나 고정 section이 필요하지 않다. 파일 순서와 제목은 의미나 중요도를 자동 결정하지 않는다. 같은 task와 파일 bytes를 선택하면 입력 순서와 무관하게 같은 출력이 나온다.

선택적인 artifact는 bytes의 hash만 기록한다. snapshot은 파일 내용을 담을 수 있으므로 공유 범위를 검토하고 비밀정보를 선택하지 않는다. 파일당 기본 256 KiB, 전체 기본 1 MiB를 넘는 source는 조용히 자르지 않고 실패하며 한도는 명시적으로 조정할 수 있다. 크기 예산은 파서 자원 보호이며 모델의 토큰 예산이나 관련성 점수가 아니다.

### 원문 변경 검사는 선택한 파일과 산출물의 변경 여부만 판단하고 내용을 갱신하지 않아야 한다.

`check`는 snapshot에 저장된 source·artifact hash를 현재 bytes와 비교한다. 모두 같으면 `unchanged`와 exit 0, 변경·삭제·읽기 불가가 있으면 `changed` 또는 `unavailable`과 exit 1을 반환한다. 잘못된 schema, 중복 경로, source 내용과 hash의 불일치, repository 밖 path와 잘못된 입력은 exit 2로 거부한다. CLI는 snapshot·원문·artifact를 쓰지 않는다. 새 capture가 이전 설명을 검토했다는 증거를 만들지 않는다.

관계가 선언되지 않은 새 파일이나 선택하지 않은 dependency의 변경은 이 검사 범위에 포함되지 않는다. 저장소 밖 파일과 외부로 향하는 symlink는 읽지 않는다. 별도 root의 같은 상대 경로로 검사하면 선택한 root와 snapshot의 bytes만 비교하며 원 저장소의 신원이나 승인 여부는 인증하지 않는다.

### 문서 품질은 독자의 이해와 작업 결과로 검증해야 한다.

스펙은 필요한 동작·이유·경계·예외와 확인 가능한 결과를 설명하고 계획은 작업 순서·의존성·완료 판단을 설명한다. 제목과 순서, 파일 분할은 내용에 맞게 선택한다. 문서 검증에 실제로 쓰이는 metadata와 원문 참조는 내용 설명 뒤에 맞추고, 사용처가 없는 형식과 중복 문구는 제거한다. 원문 탐색 가능성이나 schema 통과를 이해의 증거로 취급하지 않는다.

설명 제작 전에 핵심 질문과 기대 사실을 정한다. 전달할 설명만 읽는 별도 평가에서 답과 누락·의미 왜곡을 확인하고, AI 작업에서는 같은 근거로 실제 동작과 예외를 확인한다. 제목 변경·순서 변경·한국어 서술 같은 입력 차이로 의미가 사라지지 않는지 점검한다. Agent 평가와 사람의 이해도 측정은 구분해서 보고한다.

## Decisions & History

- 2026-09-22 [CURRENT] 같은 원문을 기반으로 작업 컨텍스트와 독자 설명을 제공한다. 고정 시각 템플릿은 제거한 상태로 유지하고 출처·변경 추적을 표현과 독립적인 선택형 도구로 제공한다. 사용처가 없어진 Plan parser와 고정 형식은 제거한다. 현재 사용되는 Spec 무결성 검증은 실제 기능의 가치로 판단하며 기존 호환성은 설계 제약이 아니다.
