# Forge에서 계속 강제할 원칙과 줄일 실행 절차

조사일: 2026-09-10  
검토 기준: `61eabcdbd7cb87545c09d75f1c893e709a1cf736`, Forge `0.1.23`  
문서 성격: 분석과 개선 제안. 승인된 Canonical Spec이나 실행 계획을 대체하지 않는다.

Forge는 개선할 필요가 있다. 요청한 결과를 끝까지 완성하고, 승인된 계약을 지키며, 실제 증거로 완료를 판단하는 원칙은 유지할 가치가 높다. 반면 질문의 개수, 테스트 작성 순서, 태스크별 모델 등급 기록, 고정된 문서 양식까지 모든 작업에 적용할 근거는 약하다. 이 절차들은 결과에 도움이 되는 경우에 선택하도록 바꾸는 것이 적절하다.

이번 검토에서 확인한 것은 규칙의 존재·중복·충돌 가능성과 공식 플랫폼 문서의 변화다. 축소 버전의 실행 시간, 비용, 결함률이 개선됐다는 실험 결과는 아직 없다. 특정 최신 모델이면 검증이나 프로젝트 지식이 필요 없어진다는 결론도 내리지 않는다.

## 검토 범위와 현재 상태

- 배포 스킬 14개의 `SKILL.md`, 주요 실행·이식성 참조, 세션 시작 훅, 유지보수 규칙과 관련 정책 검사를 읽었다.
- 정본 workflow의 관련 항목, 완료된 009·010 개선 계획과 기존 검증 기록을 확인했다. 모든 스크립트의 구현이나 모든 테스트를 감사한 것은 아니다.
- OpenAI·Anthropic 공식 문서와 Anthropic의 하네스 실험, Superpowers 공식 저장소를 비교했다. Claude 앱은 코딩 작업에 해당하는 Claude Code 데스크톱 기능을 기준으로 삼았다. 일반 채팅·Cowork에 같은 기능이 있다고 가정하지 않았다.
- 스킬 본문은 `wc -l plugins/forge/skills/*/SKILL.md` 기준 총 1,950줄이다. 라우터·디버깅·TDD·검증 본문만 합하면 554줄이다. 모든 파일이 매 작업에 로드되는 것은 아니며, 줄 수는 토큰 수나 실행 비용의 측정값이 아니다.

이미 [009 개선 계획](../plans/009-forge-purpose-alignment/plan.md)과 [010 개선 계획](../plans/010-quality-first-proportionate-verification/plan.md)에 작은 작업의 직접 실행, 부분 검증, 기존 증거 재사용, 불필요한 테스트 프레임워크 배제, 승인 재사용이 반영돼 있다. 따라서 문제를 “Forge는 매번 전체 테스트와 계획을 강제한다”로 설명하면 부정확하다.

현재 문제는 이 완화 원칙 아래에도 개별 기법을 의무화하는 문장과 세밀한 형식 규칙이 남아 있다는 것이다. 일부 규칙은 정본·스킬·참조·정책 검사에 동시에 들어 있다. 상위 문장만 부드럽게 바꾸면 하위 규칙이 종전 행동을 계속 요구할 수 있다.

이 자료들은 축소 실험의 근거다. Forge 자체의 성능 향상을 입증한 자료는 아니다. 모델의 자율 실행 능력, 앱의 실행 지원, 프로젝트별 계약 지식은 서로 다른 문제다. 앞의 두 가지가 발전해도 마지막 것은 자동으로 제공되지 않는다.

### 수치 규칙의 예: 44px

44px은 터치 조작성의 좋은 기본값이 될 수 있다. 하지만 WCAG 2.2의 모든 웹 UI에 적용되는 유일한 최소값이라고 설명하면 부정확하다. [2.5.8 Target Size (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)은 AA 기준의 24×24 CSS px와 예외 조건을, [2.5.5 Target Size (Enhanced)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html)은 AAA 기준의 44×44 CSS px와 예외 조건을 설명한다. Forge가 더 큰 기본값을 선택할 수는 있지만, 접근성 목표와 제품 환경을 확인하는 원칙과 구별해야 한다.

### 실제로 오래된 플랫폼 가정

[이식성 표](../../.agent-extensions/maintaining-forge/skills/maintaining-forge/references/portability-rules.md) 111행은 Codex에 `No plugin hook support`라고 적고 있다. 현재 [공식 Hooks 문서](https://learn.chatgpt.com/docs/hooks#plugin-bundled-hooks)는 활성화된 플러그인의 `hooks/hooks.json` 로드와 manifest의 hooks 설정을 지원한다고 설명한다. 플러그인 훅은 검토·신뢰 설정을 거쳐야 한다.

따라서 이 문구는 갱신 대상이다. 다만 문서상 지원과 현재 사용자의 설치에서 훅이 실제 실행되는지는 별개이며, 이번 조사에서는 로컬 훅 활성화·실행을 시험하지 않았다. 이를 근거로 새 훅을 자동 설치하거나 전역 설정을 바꿀 이유도 없다.

|---|---|---|
| 사용자 의도와 승인된 계약을 임의로 바꾸지 않음 | 모델의 능력만으로 사용자가 원하는 정책을 알 수 없다. | 짧은 공통 원칙과 프로젝트 정본 |
| 결과·회귀를 실제로 확인하고 증거 범위만 보고함 | 코드와 테스트가 같은 잘못된 가정을 공유할 수 있다. | 공통 원칙, 작업에 맞는 검증 |
| 현재 계약·제안·실행 기록·생성 뷰의 권위를 구분함 | 계획이나 렌더링 결과가 제품 정책을 대신하면 후속 작업이 잘못된다. | 정본 스킬과 구조화 문서 도구 |
| 재개에 필요한 진행 상황과 결정을 보존함 | 앱의 대화 보존이 다른 사람·앱에 공유할 프로젝트 기록을 모두 대신하지 않는다. | 기존 작업 기록, 필요할 때 파일 |
| 원자적 문서 전환·경로 보호·소유권 충돌·비밀정보 방지 | 자연어 주의사항보다 도구가 검사할 수 있는 불변 조건이다. | validator·extension manager·필요한 저장소 검사 |
| 요청한 시각 문서의 출처·재생성 가능성·실제 가독성 | 일반 diff 뷰가 제공하지 않는 Forge 고유의 산출물 가치다. | 선택적으로 호출하는 Visual Docs 도구 |
| 제품·지원 문구의 사실성과 팀 고유 말투 | 일반 모델 능력과 별도로 사용자의 취향·운영 원칙을 전달한다. | 필요할 때 읽는 tone 지식과 예시 |

권한·배포·설정 충돌에 관한 보호도 유지한다. 앱이 명령 실행을 허용하는 것과 사용자가 제품 정책 변경을 승인하는 것은 같은 의미가 아니다. 반대로 이미 구체적으로 승인한 작업에 Forge가 별도 승인 의식을 반복할 필요도 없다.

## 제안하는 최소 공통 원칙

다음 문구는 축소 방향을 보여 주는 초안이며 아직 적용된 스킬은 아니다.

1. 요청의 목표와 완료 조건을 파악한다. 결과나 범위를 바꿀 불명확함은 사용자에게 질문하고, 직접 확인할 수 있는 사실은 조사한다. 안전하고 가역적인 세부 선택은 판단해서 진행한다.
2. 사용자의 요청과 승인된 프로젝트 계약을 따른다. 계약 변경이 필요하면 변경 의미와 영향을 명확히 하고, 기존 권한으로 결정할 수 없는 선택만 확인한다. 장기적으로 필요한 결정은 정본에 반영한다.
3. 승인된 범위의 작업을 끝까지 수행한다. 복잡하거나 중단·협업 가능성이 있는 작업은 필요한 계획과 진행 상황을 남긴다. 기존 기록을 재사용한다.
4. 결과와 위험에 맞는 방법으로 검증한다. 기존 테스트를 활용하고, 동작의 정확성이나 회귀 보호에 필요한 테스트를 추가한다. 기대 결과는 사용자 요청과 계약에서 가져온다. 구현을 그대로 복제하는 테스트는 피한다.
5. 문제가 생기면 증거로 원인을 좁히고 가설을 시험한다. 같은 추측을 반복하지 않으며, 근본 해결·완화 조치·미확인 상태를 구분한다.
6. 현재 앱의 기능과 사용자 설정에 맞춰 도구·위임·검토 방식을 선택한다. 사용자 작업을 보호하고, 허용 범위 밖의 효과에는 필요한 권한을 확인한다.
7. 요청과 영향받는 계약이 검증되면 마무리한다. 유효한 증거를 재사용하고 확인하지 못한 부분은 정확히 알린다.

사용자가 제안한 “불명확하면 질문한다”, “결과 확인을 위해 적절한 테스트를 작성한다”는 방향과 부합한다. 다만 질문에는 **결과를 바꾸는 불명확함**, 테스트에는 **관찰 가능한 결과와 회귀 보호**를 남기는 것이 좋다. 이 짧은 기준이 불필요한 질문과 형식적인 테스트를 줄이면서 판단의 목적을 유지한다.

[writing-plans](../../plugins/forge/skills/writing-plans/SKILL.md) 127행의 `write appropriate tests` 금지도 적용 위치를 구분해야 한다. 스킬 수준에서 테스트 선택을 위임하는 원칙은 타당하다. 그러나 문맥 없이 전달하는 개별 태스크에 그 문장만 적으면 원하는 결과가 빠질 수 있다. 그런 태스크에는 테스트 구현법 대신 “중복 요청에도 결제가 한 번만 기록됨을 확인한다”처럼 관찰할 결과를 알려 주면 된다.

## 스킬 구성 방향

새 옵션과 모드를 많이 추가하면 다시 선택 비용이 생긴다. 우선 기존 이름·설치 경로를 유지하면서 강제 호출과 본문을 줄이는 편이 낫다.

| 현재 구성 | 제안 |
|---|---|
| `using-forge` | 공통 원칙과 최소 적용 안내로 축소. 설명·조사 질문에도 전체 실행 절차를 적용하는 트리거 재검토 |
| `verifying-work` | 짧은 증거 원칙 유지. Canonical lifecycle의 상세 판정은 해당 참조로 분리 |
| `test-driven-development` | TDD를 원할 때 사용하는 전문 방법으로 유지. 모든 로직 변경의 자동 필수 경유지에서 제외하는 안 평가 |
| `systematic-debugging` | 증거 중심 문제 해결 원칙 유지. 재현·이분 탐색·추적 기법과 고정 단계는 참고 자료로 이동 |
| `writing-plans`, `executing-plans` | 계획·실행 기능은 유지. 고정 등급·원장·중복 체크리스트 축소. 두 스킬 통합 여부는 사용 사례를 본 뒤 결정 |
| `writing-specs` | 승인된 계약과 제안의 구분 유지. 일반 원칙과 구조화 bundle 작성·전환 설명 분리 |
| `web-app-design`, `website-design` | 실제 화면 검토와 제품별 설계 판단 유지. 선언문·수치·측정 목록은 목적에 맞는 선택형 가이드로 전환 |
| `visual-docs` | 요청형 도구로 유지. 도표 선택·레이아웃·출처 규칙 중 자동 계산 가능한 부분은 도구가 처리 |
| `writing-tone`, `marketing-tone`, `operations-tone` | 팀 취향·사실성 기준 유지. 겹치는 일반 작문 교과서·절차·선언을 줄이고 목적별 예시 중심으로 구성 |
| `creating-agent-extensions` | 실제 manager 인터페이스·소유권·충돌 보호는 유지. 매번 읽는 구조 설명과 중복된 작성 의식은 축소 |

구조화 정본과 Visual Docs의 상세 구문은 실제 프로그램이 소비하는 인터페이스이므로 단순히 지우면 안 된다. 기존 자료와 링크가 계속 작동하도록 두고, 작성기가 구조를 채우거나 필요한 순간에만 참조하는 방식으로 에이전트의 부담을 줄인다. 문장 ID 교체·새 스키마·기존 bundle 전면 이주는 이번 개선의 전제조건으로 삼지 않는다.

## Superpowers와 하네스는 지금도 유효한가

[Superpowers 공식 README](https://github.com/obra/superpowers)는 현재도 설계 확인, 구체적인 구현 계획, red/green TDD, 서브에이전트 실행·검토를 핵심 방법론으로 설명한다. 이 방식의 존재와 채택이 모든 작업에서의 우월성을 증명하지는 않는다. 반대로 모델이 발전했다는 사실만으로 방법론 전체가 무효가 되지도 않는다.

Forge에 필요한 것은 과거 모델에 맞춘 수행 순서를 그대로 보존하는 일보다, 현재 환경에서도 도움이 되는 부분을 확인하는 일이다. 복잡한 다단계 변경·약한 검증 환경·문맥 없는 인계에는 상세 계획과 별도 검토가 여전히 도움이 될 수 있다. 작은 변경·충분한 문맥·명확한 테스트 환경에서는 같은 절차가 불필요할 수 있다.

특히 기존 [maintaining-forge](../../.agent-extensions/maintaining-forge/skills/maintaining-forge/SKILL.md)의 pressure test는 gate를 우회하지 않는지에 초점을 둔다. 축소 실험에서는 이 기준만 쓰면 기존 절차를 유지하는 쪽이 자동으로 유리하다. 평가 대상을 **규칙 준수 횟수**에서 **결과 품질과 필요한 제약의 보존**으로 바꿔야 한다. 불필요한 승인 질문·테스트·문서·재실행을 추가하지 않았는지도 평가한다.

## 적용 전에 확인할 실험

이 항목은 후속 검증 제안이며 이번 조사에서 실행하지 않았다.

비교 조건은 동일한 모델·앱·프로젝트 상태·사용자 요청으로 맞춘다. 현재 Forge, 최소 원칙 후보, 필요하다면 Forge 없는 기본 환경을 비교한다. 다른 모델의 결과를 섞어 스킬 개선 효과로 해석하지 않는다. 기능의 유무와 효율은 Codex와 Claude Code에서 각각 확인한다.

| 사례 | 결과 평가 | 과잉 절차 평가 |
|---|---|---|
| 분명한 문구·스타일 변경 | 요청한 표시와 주변 가독성 | 새 계획·테스트 프레임워크·무관한 조사 여부 |
| 결과가 모호한 기능 요청 | 중요한 선택을 확인하고 의도를 보존했는가 | 저장소 사실 질문, 독립 질문의 불필요한 순차 대화 |
| 재현 가능한 로직 버그 | 재현 해결, 실제 회귀 보호 | 테스트 순서 자체를 위한 재작업 여부 |
| 간헐 장애·로컬 재현 불가 | 로그 기반 가설, 적절한 완화, 불확실성 보고 | 완벽한 재현을 기다리며 가능한 조치까지 막는가 |
| 정확히 지시된 계약 변경 | 지시한 의미와 정본·구현 일치 | 같은 결정의 재승인 여부 |
| 권한·저장·공개 API 변경 | 승인 범위, 호환성, 오류·복구 동작 | 형식 축소를 계약 검증 생략으로 오해하는가 |
| 여러 세션에 걸친 작업 | 복구 지점, 사용자 작업 보존, 통합 결과 | 앱과 파일의 중복 원장, 불필요한 모델 등급 기록 |
| UI·시각 문서 | 실제 화면·핵심 상태·출처와 읽기 품질 | 관계없는 전체 매트릭스·수치 측정 반복 |

품질은 요청 충족, 숨겨 둔 결함, 회귀, 무단 계약 변경, 사용자 수정 필요량으로 평가한다. 비용은 완료까지의 시간, 토큰, 도구 호출, 사용자 개입, 중복 검사와 산출물로 기록한다. 모델 변동성을 고려해 대표 사례를 반복하고 실행 순서를 섞는다. 가능하면 어느 후보인지 모르는 검토자가 결과물을 평가한다.

첫 축소 순서는 공통 형식·선언·모델 원장, 질문 형식과 테스트 순서, 계획·검증 상세 기록 순이 적절하다. 한 묶음씩 바꾸고 품질 저하가 생긴 사례에서 필요한 지침만 복원한다. 초기 시나리오에서 문제가 없었다는 사실을 모든 프로젝트의 품질 보장으로 해석하지 않는다.

실제 수정 시에는 정본의 해당 의미, 배포 스킬, 유지보수 runbook·이식성 규칙, 정책 검사와 manifest 설명을 함께 맞춰야 한다. 기존 파서가 소비하는 문법과 안전 불변 조건은 보존한다. 조사 결과만으로 배포 스킬 변경이나 전역 설정 변경은 실행하지 않았다.
